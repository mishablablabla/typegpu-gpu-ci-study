# Lavapipe research baseline — frozen package (phase 1)

Freeze time: 2026-10-19. Scope: Lavapipe (Mesa llvmpipe 25.2.8 / LLVM 20.1.2 through Dawn `dawn.node` from `webgpu@0.6.2`), with Metal as the reference run on the same inputs. **No SwiftShader work was done.** TypeGPU sources, tests and configuration untouched; no harness policy or earlier baseline changed (§9).
Categories (as used everywhere): **accepted** = value inside a bounded interval produced by the real WebGPU CTS implementation (not proof of correctness); **rejected** = outside one (not by itself a backend defect); **indeterminate** = NaN operand (the CTS cannot build an interval) or unbounded interval (any output accepted); **unverified** = no result to judge (CPU threw / not implemented).
Machine-readable: [coverage-matrix.json](coverage-matrix.json) (generated by [build-baseline.mjs](build-baseline.mjs) from the files on disk), [runtime-ci.json](runtime-ci.json); hashes: [evaluator-versions.sha256](evaluator-versions.sha256), [manifest.sha256](manifest.sha256).

## 1. What existed and what was missing at the start of phase 1
Existing: groups A–D on Metal, ARM64 Lavapipe container and native x86_64 (f32, bit-exact dumps with f64 `want`); CTS spec files for A–D only on Metal (+ partial ARM64 summaries, no logs for A); legacy `mod/log/log2/pow` evaluated by older scripts on lossy/f32-`want` dumps; nothing for f16.
Missing (confirmed by two read-only audits of the files): native x86_64 CTS for the 17 spec files of the extended set (an earlier planning note said "16": a miscount, see §3); ARM64 CTS for group A; f64-`want` dumps/evaluations of the legacy ops on any backend; group E; provenance for Metal runs; evaluator hash record. Hazards recorded: `npm run conformance` (`scripts/run.mjs`) does `rmSync(reports/)`; plain `npm test` runs the whole conformance suite (23–38 s) — neither was run.

## 2. Oracle precision gap (legacy ops) and its fix
`allrows-bits/*` stored the harness oracle value `want` as f32 bits (`dump-allrows-bits.test.ts`): measured effect on the f64 values of the saved Metal data — lanes whose `want` is not f32-representable: mod 0 of 31 360 (exact remainder is representable), **log 470 of 480, log2 450 of 480, pow 4 360 of 5 470** (relative rounding error up to 6e-8, i.e. up to ~0.5 ULP, enough to move ULP-bound verdicts). Fix: the extension dump (`dump-bits-ext.test.ts`) writes `want` as f64 bits; the evaluator decodes 16-hex values as f64; inputs/cpu/gpu stay f32 (or f16) bits by construction. The legacy ops were then dumped again on Metal, ARM64 and native x86_64 (groupL) and evaluated with the same evaluator. Old-verdict recomputation: **0 mismatches** on all of them.

## 4. Group E — f16 (supported, executed)
Lavapipe exposes `shader-f16` (recorded in each dump's `shaderF16.adapterFeatures`); the harness requests it when present (`harness.ts`: `requiredFeatures: hasF16 ? ['shader-f16'] : []`). Evaluated with the real `FP.f16` intervals and f16 bit decoding (4-hex). Result: categories identical on all four configurations and **bit-identical GPU and CPU values in all 3 549 lanes on Metal, ARM64 and both native x86_64 runs** (0 NaN-sign differences: no NaN/inf in the f16 input list), CPU = GPU in every lane. Limitation: the f16 harness list has only 13 values per argument (169 rows per type), so this is a thin sample; the 224 `pass → indeterminate` lanes are overflow-edge cases (e.g. 65504 + 65504) where the CTS interval is unbounded.

### 5a. Independent evaluator audit
A read-only workstream audited the evaluator **before** the optional hardening (verdict: *fit to freeze, no blocking must-fix items*). Verified by it: (Q1) all 41 610 legacy lanes keep `want` as 16-hex f64, old-verdict recomputation uses it, and the stored `want` equals `Math.%/log/log2/pow` of the decoded f32 inputs in **all 41 610 lanes** (0 mismatches, Linux-produced vs macOS-recomputed); inputs/gpu are f32 by construction, nothing rounds `want`; (Q2) its own independent evaluator (real `FP.f32/FP.f16` intervals) reproduces the category counts of `groupL/lavapipe-arm64-run1` (gpu 9 748 accepted / 6 896 indeterminate / 0 rejected at row level, 16 op/type groups, 41 610 lanes) and `groupE/lavapipe-arm64-run2` with 0 differing groups (the eval.json holds counts, not per-lane data, so a lane-by-lane comparison was not possible); (Q3) every `CTS_FN` entry exists with the right arity and argument order (`mod` = float `%` → `remainderInterval`, `div(x,y)`, `pow(x,y)`), f16 uses `FP.f16` with the f16 flush thresholds and round-to-nearest f16 encoding; (Q4) NaN/−0/±inf survive both paths, the length-based decoder never sees a 16-hex `want`, scalar-broadcast lane rule consistent in all scripts; (Q5) `accepted` is produced only by `lo <= got && hi >= got` after a real interval; (Q6) `groupsABC-before-D.sha256`: 154 OK, 0 mismatches.
Gaps it listed and what was done: (1) half-infinite/NaN interval bound → now throws (invariant); (2) `dec()` accepts only 4 or 8 hex digits → now throws otherwise; (3) f16 `sub` test added (+ `dec` refusal test); (4) hashes of D/E/L dumps → `manifest.sha256`. Not done: unit tests for `worst()` aggregation, vector f16 judge, the `compare-*` scripts and the old-verdict path (covered only by the `oldRecompute` counters). After the hardening: 49/49 self-tests, **all 27 valid `eval.json` re-generated byte-identical** (2 further files differ only in the stale `input` path, see above), dumps hash-identical. Only the frozen (post-hardening) evaluator hash is recorded (`evaluator-versions.sha256`); the audited pre-hardening file was overwritten in place and **its hash was not recorded**. The association of every reported result with the frozen evaluator is established by reprocessing instead: re-running the frozen evaluator on every valid dump reproduces the stored `eval.json` byte-for-byte (§11-C), so no result depends on the unrecorded version.

## 6. Reproducibility status
- ARM64 Lavapipe: group C dumped 4× — byte-identical; other groups 1 run each.
- Native x86_64: 2–4 runs per group on 5 CPU models (AMD EPYC 7763, 9V45, 9V74; Intel Xeon 8573C, 6973P-C; a sixth, Xeon 8370C, appears only in an invalid attempt); **GPU values identical to ARM64 in every lane of every group**. Bit patterns differ only in the sign of NaN produced by invalid operations (ARM `7fc00000`, x86 `ffc00000`): legacy ops 1 799–1 815 GPU lanes, B 39–43, C 41–42, D 42, A 70, E 0; and **NaN signs vary run-to-run on x86_64 on the same CPU model** (group C: one lane; legacy: 16 lanes between two hosts) — so verdicts treat NaN as indeterminate and bit-identity claims exclude the NaN sign.
- Metal vs Lavapipe: value differences exist (flush-to-zero, division/transcendental approximations, NaN vs ±inf), always inside the same CTS category (`categoryChanges = {}` in every pair); legacy ops: 10 590 lanes differ in value, 461 rows differ in old status, 0 in CTS category.
- Not repeated: CTS extended on x86_64 (one run), Metal runs (1 each, local), groups A/B/D/E/L on ARM64 (1 run each).

## 8. Known limitations, exclusions, unresolved
- Intervals are computed by the evaluating host; the Linux-aarch64 check matched macOS, x86_64 Linux not checked.
- 12–16% of GPU lanes are indeterminate in every group (inputs outside the CTS domain, overflow edges, NaN/inf operands) — the CTS cannot constrain them.
- Harness input lists are not the CTS's own lists; CTS spec files passing and lanes accepted are separate facts. Group C/D/E sample sizes are small (880 / 360 / 1 521 rows).
- Mechanisms (Metal flush and division approximation, NaN sign, tanh near zero) are characterised, not traced into Mesa/Metal sources; Mesa/Dawn source line references from earlier reports remain unverified offline.
- Unresolved from earlier work: Lavapipe `log/log2` of subnormal inputs (spec-silent; CTS interval unbounded; legacy dumps: 40 lanes `fail → indeterminate`), intent of TypeGPU's vector-construction rejection of NaN/inf, the three strict ported assertions. Not investigated further (no effect on baseline validity).
- Explicit exclusions: SwiftShader, hardware GPUs, operations outside A–E/L, browser benchmark, integer operations.

## 11. Final audit and closure (2026-10-19)
**Decision: PASS WITH DOCUMENTED LIMITATIONS.** Checked against the files on disk, not against earlier reports. Defects found were documentation/provenance wording only; no result, hash or count changed.

**A. CTS coverage reconciled.** See §3: 23 original + 1 PoC-only spec file; ARM64 and native x86_64 24 files / 1 162 cases, Metal 23 / 1 159, all pass, 0 warnings/skipped/failed, per-file counts recomputed from the logs by an independent script and equal to `coverage-matrix.json`. "16 missing files" was a miscount of a 17-item list (planning note, not a gap); no required test was excluded.

**B. Integrity.** `manifest.sha256`: 825 files = every file of `final/` except itself, 825 OK / 0 failed from `final/`; evaluator and tooling hashes (33) verify from the PoC root; `groupsABC-before-D.sha256` 154 OK; PoC baseline manifest 373 OK + 2 expected staging differences; TypeGPU checkout clean at `e893ad11`; staging repo clean at `8036460` = `origin/main`. All 16 raw dumps under `native-x64/` have a byte-identical twin in a group directory.

**C. Reproducibility tiers.**
1. *Repeated experiments:* group C on Lavapipe ARM64, 4 runs, byte-identical dumps (same host); groups A, B, C, D, E, L on native x86_64: 2 runs each (C: 4) on different CPU models, GPU values identical to ARM64 in every lane (NaN sign excluded).
2. *Deterministic reprocessing of stored artifacts (re-done at closure):* evaluator self-tests 49/49; frozen evaluator re-run on all 34 dump directories under groups: 27 valid `eval.json` byte-identical, 2 valid (`groupC/x64-epyc9v45-run39249118340`, `…9v74-run39249133462`) differ only in the stale `input` path (their fresh outputs are `eval.after-rename.json`), 2 invalid E native attempts reproduce their 0-group output, 1 invalid (`groupA/metal-run1`, f32 `want`) differs by design, 2 invalid E dumps have no eval; Linux aarch64 container evaluator output byte-equal to macOS for 4 dumps; 154 A–C dump hashes unchanged.
3. *Observed once:* extended CTS on native x86_64 (and on ARM64, Metal); A, B, D, E, L on ARM64 and Metal; every Metal run.
4. *Not established:* evaluator parity on Linux x86_64 (only aarch64 and macOS tested); Metal provenance beyond the after-the-fact host note; the pre-hardening evaluator hash; digest of the base image/apt packages (versions observed identical, not pinned).

**D. Scope of the conclusions.** `rejected = 0` means no lane fell outside a bounded CTS interval for *these input lists*; it does not prove the backend is correct. `accepted` = inside the interval; 12–16 % of GPU lanes are `indeterminate` (not pass, not fail); CPU `unverified` lanes are a TypeGPU CPU-path property and are never mixed into GPU counts. Metal differences (flush-to-zero results, division/transcendental approximations), x86 vs ARM NaN sign (varies run-to-run on x86), subnormal behavior of `log/log2` and the thin f16 sample (13 values per argument) are observations, not explained mechanisms. Legacy `mod/log/log2/pow` numbers come only from the f64-`want` dumps (group L). TypeGPU's rejection of NaN/inf in vector construction and the strict ported assertions remain unresolved.

**Limitations (all non-blocking) and Phase 2 mitigation.** (1) Single-run items (tier 3): a later backend difference smaller than run-to-run noise cannot be excluded for those items; Phase 2 should compare SwiftShader against these runs by CTS category, not by single bit patterns, and repeat any SwiftShader dump it relies on. (2) Metal dumps lack per-run provenance: use Metal only as a secondary reference. (3) Unpinned base image/apt/runner: Phase 2 must record digests/versions in its own `env.txt`. (4) Evaluator not checked on Linux x86_64: run `selftest-evaluator.mjs` and re-evaluate one dump wherever Phase 2 evaluates. (5) Dump-test version `26d590df` for 6 A/B dumps: data-equivalent; reuse the frozen `7ef74b00` for new runs. (6) Small C/D/E samples: do not extrapolate category shares.

Phase 1 — Lavapipe research is closed. No further Lavapipe research is planned. The baseline is ready to serve as the reference for Phase 2, subject to the documented limitations.
